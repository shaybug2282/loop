# Changes

## 2026-07-30 — Demo mode: try Loop without an account

The landing page sold the product with a static three-`div` mock and offered only one next step — Google OAuth with calendar scopes. "Try it first — no account" now drops a visitor into the real UI (dashboard, calendar, friends, groups, chat hub) against a seeded fake world: 4 friends, 2 groups, a week of calendar events, tasks, an invite awaiting replies, DM threads and a plan in flight, all dated relative to today so nothing goes stale. The whole thing hangs off one seam — `src/demo/demoFetch.js` patches `window.fetch` and answers both `/api/*` and Google's Calendar/Tasks hosts from `demoStore`, so **no widget knows demo mode exists**; the 19 files that gate on `localStorage.googleUserId` work untouched because demo mode simply sets it. Installed at module scope in `src/index.js`, not an effect: `AuthContext` validates its session on mount and logs out on a 401, which would tear the demo down before first paint. Unhandled ops return a local 501 and warn, so a coverage gap is a visibly broken widget and never a real request. **Nothing in `api/` changed** — no anonymous endpoint, no migration, no rate limiter, no Anthropic spend.

Two things are more real than they had to be. Demo DMs are genuinely end-to-end encrypted: the store generates an ECDH keypair per fixture friend and, because key agreement is symmetric, encrypts their side with the same key `ChatDirect` independently derives — and decrypts what the visitor sends back. And the scripted assistant's slot-finding is real arithmetic over the fixture calendars, so times it proposes are actually free for everyone named; only the language understanding is keyword matching. Both facts are disclosed on screen: a persistent banner ("these friends, messages and events are made up") plus a separate notice inside the assistant pane, where a scripted reply is easiest to mistake for the real thing. A second tab finding the flag with no world re-seeds rather than tearing down: the flag is shared `localStorage`, so clearing it would strip the banner and the assistant notice from the *original* tab while it kept showing fake data — disclosure gone, fake data still there. Verified by driving a real browser: 16 checks on the main path (enter, seeded widgets, calendar, DM decrypt and round trip, both notices, plan cards, exit clears storage, zero network requests leave the browser, zero console errors) plus 10 more on the composer entry point, booking write-through, the Groups section and the mobile layout — and `CI=true` build clean, 76/76 unit tests. Potential bugs to watch: coverage is incremental, so any op without a handler 501s and breaks that widget in demo mode only; the demo patches a global (`window.fetch`), and while exit restores it and hard-reloads, that's the piece most likely to break subtly; and `--dm-banner-h` is measured by a `ResizeObserver` because the banner wraps to ~84px on a phone — if that measurement ever fails, the sticky page header lands inside the banner and loses to it on z-index, hiding the only nav on mobile.

## 2026-07-30 — One chat hub: DMs, groups and scheduling in a single window

Messaging was the same interaction three and a half times over — `MessagesPanel`, `GroupChatPanel` and `AssistantPanel` each docked in a shared bottom-right rail behind their own context, plus six places that rendered `SchedulingAssistant` in a modal of their own (CalendarPage, FriendsPage ×2, GroupsWidget, EventPopup, NewEventPopup). All of it collapses into `ChatHub`: one centred 960×680 window with Direct / Groups / Plans sections, opened by a persistent bottom-right launcher (`ChatLauncher`) that works on every page, driven by one `ChatHubContext` with a single `openChat({ section, target })` entry point. Every caller lands where the click came from — the dashboard composer and Calendar's "Find a time" open Plans, a group tag opens that group's thread, a friend's Message button opens that DM — and all of them are reachable from the launcher afterwards. Nav loses both `Messages` (the launcher replaces it) and `Groups` (it pointed at `/friends?tab=groups`, a tab of the page `Friends` already opens), in the header and the drawer; `isActive` in both now treats `/friends` as owning all three of its tabs. Only the active section mounts, so opening the hub to look at plans no longer pays for ECDH key generation, a `store-key` round trip and a 3s DM poll it isn't using. Below 720px the window is a full-screen sheet showing one pane at a time.

Deleted: the three panels, the three contexts, `.dock-rail`, and the seven now-orphaned CSS blocks that styled the old nested modals. The hub moved off the old `--z-panel` (900) layer to `--z-modal-deep` — as a `role="dialog"` with a full scrim it would otherwise have opened *underneath* every modal in the app (`--z-modal` is 1000), and the message context menu moved above it for the same reason. Verified: clean `CI=true` build, 66/66 tests, `node --check` on every `api/` file. Potential bugs to watch: the launcher badge counts **unread DMs only** — `MessageToast`'s poll is the app's sole unread signal and the API exposes no group or plan equivalent, so it under-reports; `NewEventPopup`'s assistant hand-off now closes the popup and opens the hub, so a booking made there no longer fires that popup's `onCreated` callback (the dashboard's own refresh covers it, but a caller relying on the callback would not see it); and none of this has been exercised in a browser yet — the window sizing, the mobile sheet and the launcher position are unverified against real pixels.

## 2026-07-14 — Real authentication: session cookies + Google authorization-code flow with refresh tokens; launch cosmetics

**Session auth (every endpoint).** The API no longer trusts client-supplied `googleId` for identity — previously anyone who knew a Google id could read/modify that user's friends, events, messages, profile, and settings. Sign-in now runs the GIS **authorization-code** popup flow: the browser gets a one-time code, `api/user.js` op:`google-auth` exchanges it server-side (`GOOGLE_CLIENT_SECRET` env var, new — **required**), validates the `id_token` claims (aud/iss/sub; `sub` equals the legacy userinfo id so existing rows match), upserts the user, and sets an httpOnly `SameSite=Lax` `loop_session` cookie holding an HMAC-signed `{uid, gid, exp}` token (30-day TTL; key = `SESSION_SECRET` or derived from `TOKEN_ENCRYPTION_KEY`; helpers + `requireUser`/`parseCookies` in `api/_lib.js`, unit-tested in `src/__tests__/api-session.test.js`). Every op in all six routers now derives identity from that cookie and 401s without it (the only public ops are `google-auth` and `logout`); the insecure `op:'sync'` (client-pushed tokens) is gone, `create-event` now also rejects invitees who aren't the caller's friends/group-mates, and CSRF is covered by Lax + JSON-POST-only mutations. Clients still send `googleId` params — they're ignored (documented in CLAUDE.md); `AuthContext` validates the session on load (op:`session`) and clears the cookie on logout.

**Refresh tokens (migration 016 — run `db/migrations/016_users_refresh_token.sql`).** The code exchange yields a refresh token, stored encrypted in `users.refresh_token`. New `getGoogleAccessToken` (`api/_lib.js`) transparently refreshes expired access tokens and persists them; ALL server-side Google calls now use it (free/busy in `api/ai.js`/`api/friends.js`, profiler calendar reads in `api/_profiles.js`, event create/cancel in `api/schedule.js`) — fixing the silent core failure where any participant offline >1 hour looked like an empty calendar and confirmed events silently never reached Google Calendar. The browser now fetches short-lived access tokens from `GET /api/user?op=google-token` (in-memory cache in `googleCalendar.js`; tokens no longer live in localStorage; the refresh token never leaves the server). OAuth scopes narrowed: full `calendar` replaced by `calendar.readonly` + `calendar.events`.

**Launch cosmetics.** Login page's Google button finally styled (`.google-sign-in-btn` had no CSS — rendered as a bare browser button in production); footer placeholder joke replaced with "© 2026 Loop"; privacy policy now references hangoutwithyourfriends.fun instead of the old vercel.app URL; guest dashboard is a proper landing (Loop brand header, 3-step how-it-works cards, 30-second auto-popup sign-in modal removed — modal now opens on CTA only, guest sidebar gone); `NewEventPopup` gains an Event-name field (manual events stop being title-less "Hangout"s); dashboard gets a 2-column tablet layout (769–1080px, Friends spans below); status chips (pending/confirmed/declined/rain-check) moved to new `--status-*` theme tokens with dark-mode values, fixing unreadable light chips on dark surfaces; dead `find-times` op + `findFreeSlots` + its test pruned. Also fixed en route: `seedRescheduleConversation` declared `const note` shadowing its `note` param (TDZ throw swallowed by the catch) — reschedule handoffs never actually reached the creator's assistant chat; renamed to `seedMsg`.

**Deploy checklist:** (1) add `GOOGLE_CLIENT_SECRET` (from the same Google Cloud Web client) to Vercel + `.env`; (2) run migration 016; (3) everyone must sign in again — the first new consent grants the refresh token (if Google skips the consent screen and no refresh token lands, revoke the app at myaccount.google.com/permissions and sign in once more). Potential bugs: sessions are stateless, so a stolen cookie stays valid until expiry (no server-side revocation list yet); pre-016 DBs fail open to the old behavior (tokens work only ~1 h); `verifySession` treats a missing `SESSION_SECRET`+`TOKEN_ENCRYPTION_KEY` as a thrown config error (500, caught per-request as null → 401).
